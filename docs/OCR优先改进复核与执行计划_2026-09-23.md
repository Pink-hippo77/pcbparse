# OCR 优先改进复核与执行计划

日期：2026-09-23。范围：当前源码、9月23日开发冒烟报告和产物；不把附件中的建议当作执行授权。本轮仅复核和提出方案，未修改生产源码、模型锁或启动训练。

## 结论

先精进 OCR 是合理方向：缺位号会引发器件和其引脚整体裁剪，缺引脚编号则破坏电气身份。但现有 A04 尚不能证明主要损失发生在 OCR 检测层。首个周期应先修正测量和缺失值契约，再拆分检测、识别、语义绑定实验；不宜直接开始更大规模训练。

工程进展可确认：质量入口、漏斗对象记录、裁剪计数与修复证据已经进入实现。本轮定向运行 74 项 unittest 全部通过，覆盖 A01、A03、A04、A06、多级 OCR、submission 与 repair lineage。没有重新执行用户报告的全套 709 项、torch 20 项和五图模型推理，因此这些运行结果作为已有证据阅读，不冒充本轮重跑。

## 必须先解决的复核发现

### P0：严格输出仍会伪造缺失编号

`src/pcbparse/output/official_serializer.py` 的 `serialize_official_with_quality` 仍允许空 pin number 自动编号。直接用现有 `tests.unit.test_serializer_boundary_a03.make_ir(pin_number="")` 调用 strict，实际产生 `pin_1`，quality 同时为 `pin_auto_numbered=1`、`status=strict_success`。

现有单测第100行起还在肯定这种行为，另有 degraded 模式 UNKNOWN key 填充用例。测试通过不能证明符合当前 AGENTS.md：该文件明确禁止缺 key/number 时自动编号或填充占位绕过门禁。五图报告记录的自动编号合计为139，必须与真实读出的编号分开，不可算作 OCR 成功。

建议：统一 Validator、serializer 及调用者的拒绝契约；缺失标识产生明确诊断并阻断相应正式输出，不得仅改质量标签。若已有合法降级裁剪策略，必须记录删除对象及受影响网络并重新验证，不能凭空赋号。低层 serializer 入口也要守住边界。反向修改旧单测：缺失必须失败；显式合法编号保持原样。有效空图与裁剪至空分开。

### P0：A04 的 detected 不是真正文本框检测

`src/pcbparse/evaluation/error_funnel.py:51` 已声明 owner-match proxy。`_text_field_funnel`（414行起）用器件/引脚是否匹配判断 detected，随后在全部预测字段值中寻找相同字符串来判 char_correct/field_correct（490行起），并未对 GT 文本框与 OCR 框做匹配。重复的“1”“10k”等内容可能在错误位置满足条件。

因此 115/853 不能命名为 OCR 检测召回率，738 不能直接解释为漏检文本；field_correct 也不等于字段分类准确率。它可以保留为“终态字段可恢复性代理”，但不能据此分配检测/识别优化资源。

建议：另外建立真正的文本对象评估，每个 GT 文本 ID 对应几何框、原始内容、字段类型、owner ID 和标注来源；以固定的一对一几何匹配测检测，再在匹配对上测识别、字段分类及归属。没有可信文字几何标注的对象应标 not_measured，不得用器件框代替文字框。重复字符串错位、重复候选、一框吞多词都要有回归用例。

### P1：当前 IR 已经裁剪，不能反推出原始模型召回

`pipeline/orchestrator.py:213` 调用 `_prune_unrepresentable`；`cli.py:460` 保存的是返回的终态 IR。读取五图产物得到：终态保留43个器件、200个 pin，quality 记录裁剪169个器件、341个 pin。两部分相加只能说明裁剪前预测对象数量，不能说明其中有多少是真阳性。

五图共4548个 TextToken，说明“最后字段很少”并不等于“只产生了很少 OCR 候选”。其中可能同时存在碎片、重叠重复、误识别与错归属，不能靠总数判断召回。

建议：持久化 perception 输出、association 后、裁剪前、最终 IR 四个可回放快照，使用稳定 ID 或显式映射关联，分别测器件/Pin 检测和字段缺失导致的丢弃。正式输出仍严格只有 components/pins/nets；调试快照留在独立产物。

### P1：语义类别与 ROI 归属需要独立检查

0088 的现有 token 中可见 `C2` 被标为 pinnumber。仅凭字符串不能断定这一定错误，因为字母数字 pin label 可以合法存在；但它是优先人工核验的冲突案例。`association/semantic_fields.py` 的侧边条带与 component ROI 分支会在器件类别前缀不兼容时把字母数字串作为 pin number。因此上游器件类别或 ROI owner 错误可能继续影响字段类别。

建议：分类与归属联合保留候选及拒绝理由；器件类别只作为证据之一，不能将全部不兼容位号形状字符串直接确定为 pin number。比较全图、器件 ROI 与侧条带对同一物理文本的结果，输出可视化错误样例。

## OCR 模块框架

保留现有流水线和 Circuit-IR，不重建项目。建议新增能力围绕现有模块扩展：

```text
图像与坐标变换
  → 多级视图：全图 tile / 器件 ROI / 引脚侧条带
  → 检测候选：包括识别为空而被丢弃之前的框
  → 几何恢复与跨视图合并：保留全部来源、变换和候选 ID
  → 识别候选：原文、置信度、可用时的 n-best，不静默改写
  → 字段分类：designator / value / pin number / pin name / net label
  → 对象绑定：位置、类别、相邻引脚、唯一性约束共同评分
  → Circuit-IR：明确 unresolved，不造 key / number
  → Validator → 严格官方输出

独立离线评估：GT 几何匹配 → 检测 → 识别 → 类别 → owner → 端到端字段
```

调试证据建议包含：image_id、token/candidate_id、view_id、level、原图 bbox、view bbox、坐标变换、det_score、rec_score、raw_text、候选文本及来源、field_candidates、owner_candidates、selected/rejected reason、关联后的对象 ID。无法从当前模型取得的置信度或 n-best 写 null，并说明原因，不构造概率。

### OCR-02：最能决定优化方向的实验

1. **检测实验**：使用真实图像检测框，匹配可信 GT 文本框；同时报告 precision、recall，小字高度分桶、视图来源分桶。匹配阈值在比较前固定，不能每个候选模型单独调整。
2. **识别 oracle**：仅离线把 GT 文本框裁剪送入当前 recognizer，测原始文本 exact、字符错误率 CER。若它本身差，才优先识别模型；若 oracle 好而预测裁剪差，优先框质量、padding 和缩放。
3. **绑定 oracle**：仅离线输入 GT 文本/框，分别在预测 owner 与可信 owner 条件下测分类/绑定；明确哪些依赖被替换，避免把器件检测损失算到 OCR。
4. **真实端到端**：保持 image-only 入口，测位号 exact+owner、pin number exact+owner 和裁剪率。任何 oracle 不能进入生产、正式性能报告或模型晋级证据。

这些实验分别回答“没找到”“读错了”“读对但放错了”，应先于训练。对暂无真值的项不报零。

### OCR-03：先排查预处理，而非盲目降低阈值

当前 `torch_ocr_adapter._detector_tensor` 将图像直接 resize 到检测输入宽高。需要核对训练时变换，特别是细长侧条带是否遭受形变；不能只在推理端改 letterbox 却不验证训练/推理一致性与逆变换。

先做单因素实验：基线、保持比例并 padding、提高小字视图有效分辨率、调整 ROI padding；随后才小范围探索检测阈值。当前识别阈值为0意味着低可信读数也可能进入后续链路，简单增加框数容易让匹配更差。每次比较文本召回、误报和 downstream exact+owner，不以 token 数增多作为成功。

全图 tile 与 ROI 是互补视图；合并依据原图几何与文本证据，不能按内容全局去重，因为电路中相同数字和阻值经常出现在不同位置。

### OCR-04：何时训练以及怎样构建数据

只使用 dataset300-v2 的训练部分；使用现有 `training/ocr_materialize.py` 数据来源与哈希校验能力，不另造未经校验的样本目录。训练、验证和测试按源图 grouped split 继承，同一图片的所有 tile/crop/增强必须同组。

先统计错误分布，再补充小字号、旋转文本、线条穿字、短数字、负号/小数点、大小写、字母数字 pin、长型号等真正失败类型。线段和器件轮廓可作为检测负例；需要人工确认的字符不能用模型输出直接当真值。保留原始字符串，10k、10K、10 k 的容错指标可另外列出，不能代替 exact。

训练按现有 preflight → smoke → 单 GPU 正式运行顺序，产出 candidate bundle。仅训练局部瓶颈；不把检测器和识别器同时换掉而失去归因。候选通过 image-only E2E 比较及晋级机制后才改变生产锁。

## 成功标准与报告口径

第一轮以建立可信基线为目标，不凭当前代理指标承诺目标百分比。每次比较固定输入清单、split 身份、模型锁、配置、源码摘要、评估器版本、随机种子和设备。报告纳入/排除分母。

- 检测：一对一文字框 P/R、几何匹配政策、小字分桶。
- 识别：GT crop exact/CER 与 predicted crop exact/CER，按字段分桶。
- 绑定：条件准确率与全量 exact+owner 两套分母，错误归属和拒绝比例。
- 系统：真实非空输出、字段缺失导致裁剪、未识别 pin、raw-v1 和错误案例；不能让自动补号改善指标。
- 成本：每图时间、视图数、候选数、峰值内存。当前 CPU 数据只用于 CPU 比较，不能当 GPU P95。

五图是开发回归，30张 grouped val 可用于开发比较，已反复调优的 release50 不作独立泛化。没有官方 evaluator、Docker 演练和 GPU 证据前，release_ready 保持否。
