# 系统完成度分析与下一步方案

日期：2026-08-23 23:22（Asia/Shanghai）  
审计口径：实施手册、当前工作树、冻结 Dataset300 split、训练终态文件、模型锁、readiness 与 image-only 严格端到端证据

## 技术结论

系统已经具备可持续迭代的工程骨架：数据 lineage、五任务训练入口、Circuit-IR、感知适配器、关联、图构建、Validator、Serializer、CLI/HTTP 和候选模型锁都能工作。**但现有证据不支持“高度可用竞赛系统”或“可提交生产系统”的结论。**

不建议给出一个主观总完成百分比。工程功能覆盖率与竞赛质量不是同一指标：当前工程闭环较完整，模型与严格 E2E 质量却仍有三个 P0 断点——Component 低召回、OCR/Pin 语义缺失、Junction/Graph 真值与拓扑质量不足。官方 evaluator 和 sample submission 又未出现，因此不存在可审计的官方总分。

当前最准确的发布判断是：

- **可继续开发和训练：是。**
- **可做候选 image-only 联调：是，但必须使用临时 benchmark lock 并标记为诊断。**
- **生产 ready：否。**
- **竞赛高度可用：否。**
- **可 bless 五任务：否。**

## 范围、数据与指标定义

- 数据版本：`dataset300-v2`，300 个样本，240/30/30 grouped train/val/test。
- lineage：600 个源图/标注 SHA-256 全部验证；147,758 条五任务记录；重复/近重复/同工程族不跨 split。
- 模型选择：只允许冻结 `val` 选择阈值和候选。0024 属于 `test`，只用于事后故障诊断。
- Component：官方 component 标注上的 class-aware IoU@0.5 与 mAP50。
- Pin：原图像素坐标 4px 内的一对一匹配；必须同时报告 TP/FP/FN、微平均 P/R/F1 和 pred/GT。旧 `pck_4px` 等价于召回，不能单独代表可用性。
- OCR：识别 exact match/CER 与 detector P/R/Hmean 分开报告。recognizer 通过不代表检测和设计符解析通过。
- Wire：稀疏官方路径派生的 eligible mask 上报告 skeleton/centerline 指标；不能把 pixel F1 直接当作 Net/Graph 正确率。
- Junction：六类 macro-F1 必须来自真实、可信的 val support；synthetic 仅限 train。
- E2E：严格模式要求 Validator 0 ERROR 后才能 Serializer；degraded 模式只用于定位问题，不属于正式验收。

### 不能被误读的三个“看起来不错”的数字

1. OCR aggregate exact `0.6785`、甚至 designator exact `0.9038`，都只证明识别器在已给定文本记录上的能力；它们不能覆盖 detector recall `0.3250`，也不能解释 0024 真实链路的 0/15 与 0 赋键。
2. Pin PCK `0.5189` 本质是召回；只有结合 precision `0.4249`、F1 `0.4673` 与 ratio `1.221` 才能判断候选质量。
3. Junction observed-three-class macro-F1 `0.8560` 不能替代六类指标；三类零 support 时，放宽为 observed-only 会隐藏竞赛关键 crossing 风险。

## 严格 E2E 显示的是级联失败，不是单模块小误差

现行 baseline 配置保持 Component/Wire `1024/160`。候选 benchmark lock 在 test 样本 0024 上的严格 image-only 诊断为：

| 层 | 输出/错误 | 解释 |
|---|---|---|
| 感知 | 4 components、66 pins、286 texts、606 segments、689 junctions | 所有适配器均被真实调用，不是空桩 |
| 关联 | 仅 1/4 component 获得 key；少量 pin 字段成功 | owner 与 OCR 设计符/引脚号不足 |
| 图 | 110 physical/electrical nets | 相对原始 41 edges、raw-v1 期望 38 nets，存在明显碎片化 |
| Validator | 87 ERROR：3 missing key、60 missing pin number、24 disconnected segments | 三个 P0 断点全部出现 |
| Serializer | 失败 | IR 未达到 `VALIDATED`，严格阻断正确 |
| degraded | 1 component、2 pins、106 nets；Component/Pin/Graph F1 均 0，Wire F1 `0.8010` | 可写 JSON 不等于可用提交 |

Component 512 / Wire 1024 的域分离实验能把 Component 候选提高到 20，并避免 Wire 512 带来的 segment 爆炸；OCR/Pin ROI 解耦也减少了 220 个重复/噪声 OCR token。但最新实验仍有 372 个 ERROR，严格序列化失败，且耗时上升。因此：

- **保留域分离与 ROI 解耦的代码架构；**
- **baseline 参数保持 1024/160；**
- **512 Component Tile、Pin padding 64 继续作为验证集实验，不进入生产默认。**

0024 的直接 Component 512 Tile 检测在阈值 `0.124038` 下得到 P/R/F1 `0.7619/0.5926/0.6667`，但 16 个 TP 全是 Box，C/Gnd/R 共 11 个全漏。这个 test 单例说明 Tile 值得继续研究，也同时证明不能从该样本选阈值或声称多类已解决。

## 优化路线与验收条件

### P0：形成真正可比较的候选

1. 完成正在运行的 Pin v5；只按配置中的多指标门禁、导出一致性和完整 bundle 判定，不能用 smoke 或阈值扫描代替终态。
2. 完成 Component v4；必须同时满足 mAP50 门禁、按类/尺寸召回不退化和导出/运行时一致性。
3. 为 OCR 增加 detector Hmean/recall 与 OOV/overlength coverage guard，避免只凭 recognizer exact match 放行。
4. Junction 人工复核不能省略：2,283 条 UNKNOWN cross 记录对应 1,119 个物理候选簇，当前审计没有任何 accepted-as-ground-truth 的 human-review evidence。

### P0：把严格 E2E 变成模型门禁

每个新候选除了 task val，还必须在固定且不参与调参的 image-only 套件上满足：

- Validator 0 ERROR；
- Serializer 成功；
- Component key、Pin number、Net connectivity 的 eligible 覆盖率单独报告；
- raw-v1 Component/Pin/Wire/Graph 指标不退化；
- 相同输入重复 3 次 JSON SHA-256 一致；
- 每阶段耗时、峰值显存和 prune 数量可追溯。

单个 0024 不足以作为套件。至少按 KiCad、datasheet、JLC/Altium、密集 Box/键盘、低分辨率、Tile 边界、crossing/flywire 分层，从冻结 val 选择诊断集，再把 test 保留到最终一次性评估。

### P1：图拓扑优先于继续抬高 Wire pixel F1

Wire 已是最强模块。下一轮收益更可能来自：

- 减少 skeleton 微段与重复 junction；
- 对 connected/non-connected cross 使用真实分类器证据；
- 对 gap repair、endpoint merge、pin snap 做冻结 val 分层扫描；
- 用 oracle 分析区分“Wire mask 错”“Junction 错”“Graph 参数错”；
- 报告 Net split/merge、pairwise connectivity 与 disconnected ERROR，而不只报 pixel F1。

### P1：注册与 promotion

禁止直接编辑 `models/models.lock.json` 把候选改成 blessed。每个任务必须有不可变 predictions、metrics、model card、bundle manifest、导出对齐和完整数据 lineage。最终 promotion 必须：

1. 恰好五个 verified bundle；
2. 所有文件/模型卡字节哈希复核；
3. 全任务共享数据 lineage；
4. Junction 真实六类 human-review evidence；
5. production adapter load + fixture smoke；
6. 严格 E2E 与目标机演练通过；
7. 写入新的 lock/report 路径，不覆盖现有锁。

### P2：部署与官方验收

- 获得官方 sample submission/evaluator 后再冻结 guide-v1 假设。
- 目标 Linux/GPU 镜像离线 build；验证 `/health`、`/ready`、输入只读、输出原子写、无凭据泄漏。
- 完成 30–50 例 rehearsal，证明总时长 <2h、P95、峰值显存、冷启动和失败恢复。
- Qwen 默认保持关闭；只有独立 A/B 在严格 E2E 指标、超时率、拒绝率和 Token/时延预算上有正收益时才启用。旧的“+23 引脚号”诊断不能替代正式提交质量证据。

## 风险与边界

| 风险 | 严重度 | 当前控制 | 仍需补证 |
|---|---|---|---|
| 官方格式或评分口径不一致 | Critical | guide-v1 严格 serializer；本地 raw-v1 明示非官方 | 官方 sample submission 与 evaluator |
| Component 长尾/小目标低召回 | Critical | v4 均衡采样、Tile 实验 | 全 val 分层指标与门禁 |
| OCR recognizer 指标掩盖 detector 失败 | High | 分拆检测/识别指标 | 新 detector gate 与 designator E2E |
| Pin 只报 PCK 造成假达标 | High | v5 使用 P/R/F1 与双向数量门禁 | v5 正式终态 bundle |
| Junction 三类无真实支持 | Critical | synthetic 只进 train；promotion fail-closed | 人工标注、真实六类 val |
| Wire pixel 指标与 Graph 质量脱节 | High | raw-v1 Graph 与严格 Validator | oracle 拆解和拓扑优化 |
| 没有源码版本库 | High | 文件、数据与模型 SHA-256 lineage | 初始化版本控制并固定 commit |
| Docker/目标机未验证 | High | readiness 与 Dockerfile | 目标机 30–50 例 rehearsal |

## 发布判定

在以下条件全部满足前，结论保持“未达高度可用竞赛水平”：

- [ ] 官方 schema/evaluator 已冻结；
- [ ] Component、OCR、Pin、Wire、Junction 均有当前代码/配置下的 verified bundle；
- [ ] 五任务门禁全部通过，Junction 为真实六类；
- [ ] 严格 image-only 分层套件 Validator 0 ERROR、Serializer 全通过；
- [ ] raw-v1 分项指标和覆盖率达到团队明确阈值；
- [ ] 五任务 promotion report 与 blessed lock 由权威工具生成；
- [ ] `healthcheck --require-ready` exit 0，并完成 runtime smoke；
- [ ] 目标 Docker/GPU 的 30–50 例时延、显存、确定性与失败恢复通过。
