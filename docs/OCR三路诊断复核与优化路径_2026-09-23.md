# OCR 三路诊断复核与优化路径

本轮只检查源码、已有产物并重算统计，未启动训练、改模型锁或修改业务源码。运行 test_text_box_eval、test_ocr_oracle 共22项测试，全部通过；未重跑用户所述全套747项或五图推理。

## 结论

暂不能确认“检测过滤为P0、识别P1、绑定P2”的性能瓶颈排序。识别 oracle 提供了真实识别证据，但检测采集和绑定适配仍存在实现错误，当前应先修诊断入口，再做小字映射消融。不要直接删除小框过滤器。

## 1. 汇总需明确宏平均和微平均

读取 work/ocr-triage-real/triage_report.json 的逐对象结果：

|指标|结果|含义|
|五图等权 exact|约0.637|每图权重相同，10个文本的0088与508个文本的0087同权|
|逐文本 exact|434/853 = 0.508792|853个文本中实际完全识别正确的比例|
|五图等权 mean CER|约0.171|每图平均CER的宏平均|
|逐文本平均 CER|0.251694|853个对象CER的等权平均，非总字符编辑距离/总字符数|

因此“853条汇总 exact=0.637”容易误解。报告同时列宏平均、逐文本exact和语料级CER。语料级CER需重新累加编辑距离与GT字符数，不能平均每条CER代替。

识别脚本使用真实bundle与GT裁剪，这部分证据有价值，但只是该裁剪、padding和方向策略下的识别结果，不代表检测已解决。0087占样本主体，其低准确率不应被宏平均掩盖。

## 2. 27/27不能代表0005全部候选

torch_ocr_adapter.py:311 每次 recognize 都覆盖 self._last_detection_trace。ocr_multilevel.py:103 按全局、器件ROI、侧条带分批多次调用 recognize；诊断脚本只在最后读取属性，因此拿到的可能只是最后一批。

当前 triage_report.json 的检测结论主要是文字说明，detection_recall为null；该目录没有完整逐批原始trace。已有0005.json还包含B3、R3两个器件key，至少不能把末批“全拒”直接解释成整张图没有文字进入后续链路。

修复要求：由多级调度层在每次 recognize 后立即收集该批trace，带image_id、batch_id、view_id和level；图间清空，异常路径也保存。图级数量必须等于所有批次之和。不要仅将adapter属性改为永久append，避免跨图污染和复用状态问题。

## 3. 独立检测评估仍有两处耦合错误

1. adapter的view_bbox是视图局部坐标；detection_eval.py:54直接将其与GT原图框匹配，没有应用trace中记录的transform。ROI偏移、缩放或旋转会导致错误匹配。应同时保留view_bbox与original_bbox，采用与_restore_token相同的坐标恢复机制。
2. adapter在识别为空/低分时把trace的outcome改为rejected；detection_eval仅统计outcome=kept。因此所谓检测P/R仍受识别结果影响。应拆成detected、geometry_accepted、recognition_attempted、recognition_accepted、merged等独立状态，检测框证据不可被后续覆盖。

建议分别输出原始检测、几何过滤后、跨视图合并后三套指标。跨视图重复框先报告重复率，再按明确策略合并；否则precision也会受到视图数量影响。

## 4. 绑定oracle未测到生产绑定器

两个脚本的bind_fn都含有 `if hint: return hint` 或等价分支，因此trusted=1.000是直接返回答案的结果，不能证明绑定正确。

free分支只调用infer_semantic_fields，未调用完整associate_ocr/器件文本绑定/引脚文本绑定流程；还使用GT几何，却命名为自由推断，并保留component_id优先于pin_id的旧式返回逻辑。分类分支传空组件、空引脚上下文。free=0和field=0不能证明生产系统全错，更不能说明owner推断是唯一缺口。

重建两种受控实验：
- GT文本+GT框+预测器件/Pin几何，调用真实association流程，使用预测ID→GT ID映射评价。
- GT文本+GT框+GT器件/Pin几何，仍运行真实association流程，衡量上游几何修正后的效果。

如果直接给定owner，明确标记owner已被oracle替换，不再评价owner准确率；只评价后续字段写入、冲突处理及身份一致性。

## 5. 运行入口还需对齐

- ocr_oracle_fast.py:120把未测detection_rate硬编码成0.0传入triage；必须传null/not_measured，不能自动推断检测最差。
- ocr_triage_real.py的bundle路径使用workspace_root / entry.path，而锁中的路径相对models目录；应按锁基目录解析。fast脚本已有models层。
- real脚本创建provider时未传入已加载的pipeline配置；应复用生产配置解析，显式记录实际profile、provider参数与哈希。否则与pipeline.edarace的历史运行不可直接比较。
- 两个入口写同名triage_report.json，容易覆盖不同实验；每次新run目录，保留原始逐对象证据、完整性状态、源码/模型/配置/输入哈希。

## 下一步执行路径

### 第一阶段：补齐诊断证据

先修图级trace汇总、坐标恢复、独立阶段状态、真实绑定oracle、宏微平均与入口路径。无需训练。

验收测试应包括：两批trace累加且下一张图不串数据；非零偏移ROI、缩放、旋转的原图坐标恢复；相同检测框即便识别为空，检测TP不变；可信owner不直接作为预测返回；pin/component双ID映射；缺测不填0；不等样本数的宏微平均计算。

先用0005跑通，再完成五图。报告按global/component/strip拆分各阶段候选数、真阳性损失和拒绝原因。

### 第二阶段：验证小框过滤究竟误杀什么

按原图叠加被拒框与GT文本，区分完整文字、单字符碎片、线段噪声、无有效裁剪区域。`宽高>=1像素`是连续框尺寸门槛，不是对实际像素内容的检验；既可能排除有效细小候选，也可能正确排除插值噪声。不能仅靠拒绝原因判断映射公式错了。

比较基线与有限候选策略：正确坐标恢复；对合法连续框采用floor/ceil形成非空整数裁剪；保持比例加padding；改变侧条带尺寸或小字视图分辨率。每次单因素比较，保持检测阈值、模型、输入一致。

晋级依据是被救回的GT文字、exact+owner和裁剪减少，并同时检查误报、重复数和耗时；不是保留框总数增长。不要全局删除过滤或无条件膨胀所有噪声框。

### 第三阶段：识别预处理与绑定分别优化

识别基线按434/853报告。按字段、字高、方向、长度分桶，重点检查0087；比较padding、方向与宽度策略，统计原始exact与候选top-k覆盖。保留原文，不静默替换大小写、0/O或1/I。

绑定使用修正后的真实oracle，定位位号/字母数字pin混淆、跨视图冲突、owner候选不足，再决定规则或评分修改。不能先验地定为P2。

只有GT裁剪在合理预处理下仍明显失败时，再启动dataset300-v2训练部分的识别训练；通过preflight、smoke、串行训练产生候选。所有候选先五图回归，再grouped val比较；不将这些开发数据宣称独立泛化。

## 可交给agent的任务摘要

先完成诊断正确性修复，不修改OCR权重或删除source-pixel过滤。由多级OCR调度层按图累计完整trace，统一原图坐标；分离检测、几何过滤、识别与合并状态。重写两个oracle入口调用真实association，去掉直接return hint带来的伪正确率与缺测填0，修复模型路径和配置传递。添加覆盖多批、多视图坐标、空识别、双ID和宏微平均的测试。以新run目录保存0005及五图完整诊断，之后用被拒候选可视化和同口径消融决定是否修改小框过滤。交付可复现命令、逐对象证据、真实收益与失败案例。
