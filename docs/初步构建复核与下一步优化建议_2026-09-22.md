## 3 优先处理的问题

### P0 质量接口尚未进入生产调用链

位置：[orchestrator.py](E:/EDA挑战题目六/src/pcbparse/pipeline/orchestrator.py:324)、[official_serializer.py](E:/EDA挑战题目六/src/pcbparse/output/official_serializer.py:290)、[submission_agent.py](E:/EDA挑战题目六/src/pcbparse/submission_agent.py:168)。

编排仍调用 `serialize_official`；新加的 `serialize_official_with_quality` 没有成为生产路径。旧序列化入口依然会输出 UNKNOWN 占位，但不再修改输入 IR。本次探针确认：缺 key 的合成 VALIDATED IR 经旧入口输出 `UNKNOWN_c1`，经新 strict 入口抛错。

这并不证明正常 strict 编排一定放行缺 key，因为它前面还有 Validator；它说明 serializer 的严格边界不统一，而新质量计数不会自动出现在现有生产报告中。

此外，新包装函数将 `degraded_nonempty` 直接设为 `mode == "degraded"`。本次空 IR 探针得到：输出三个空字典，但 `degraded_nonempty=true`、`fallback_empty=false`。当前 submission 则通过“是否存在 warning”判 degraded，不能可靠代表真实策略、裁剪行为和输出内容。

建议：统一一个正式序列化入口，显式传 mode；quality 随 InferenceResult 传给 submission。区分 strict_success、degraded_nonempty、empty_result、fallback_empty 和 failed_to_write，空结果与异常回退不要混为一谈。保存裁掉器件数、pin 数和影响 net 数。合法空输入可单独标记，不因为容器非空就算解析成功。

验收：使用合成 provider 跑过真实 orchestrator 与 submission，而不是只调用新包装函数；覆盖正常、缺 key、裁剪后全空、异常空回退和落盘失败。每个 case 恰好一个主状态，汇总分母等于输入图数。

### P0 A04 仍然没有可用的诊断数据

位置：[error_funnel_a04.py](E:/EDA挑战题目六/scripts/error_funnel_a04.py)、[baseline_e2e.json](E:/EDA挑战题目六/artifacts/audits/baseline_e2e.json)。

当前脚本只是包装外部传入的 counts，默认无输入也生成全零漏斗；baseline 的 image_count=null、metrics={}；oracle 是空列表。这些文件不能回答“究竟漏在 detector、recognizer、字段分类还是 owner 绑定”。

还有口径问题：脚本将 visible_labels、official_field_correct、pin_localized、net_membership_correct 排成一个连续漏斗。这些统计对象不是同一类，不能因为使用相同图片集就用后一项除以前一项作为阶段通过率。

建议分为三个对象一致的漏斗：

1. 文本字段：同一批可见 GT 字段 → 检出 → 字符正确 → 字段正确 → owner 正确 → 输出正确。
2. Pin：同一批可评估 GT pin → 定位正确 → owner 正确 → 编号/名称正确 → 完整 PinF1。
3. Net：同一批可评估 GT net → 匹配 → membership 正确 → matched-net 线段正确。

每个阶段必须携带对象 ID 的纳入和排除原因，不能只有聚合整数。没有运行或没有标注写 null/not_measured，不能写 0。GT 只在独立评估器中使用，预测清单绑定图片、源码、配置与模型。

验收：先用 5–10 张有代表性的开发图检查漏斗和错误定位，再跑完整 30 张 val。至少能为每类主要错误导出原图 ROI、预测、参考和失败阶段。没有可信 crossing GT 的 oracle 组合标记 uncomputable。

### P1 A08 测试没有证明生产引脚上限已修复

位置：[pipeline.edarace.yaml](E:/EDA挑战题目六/configs/pipeline.edarace.yaml:88)、[torch_pin_adapter.py](E:/EDA挑战题目六/src/pcbparse/perception/torch_pin_adapter.py:180)、[test_pin_geometry_a08.py](E:/EDA挑战题目六/tests/unit/test_pin_geometry_a08.py:25)。

测试检查的是 `PinAdapterConfig()` 的默认值至少 64；实际提交配置仍覆盖为每组件 12，生产 provider 会传给 adapter，再传给 decoder 的 max_detections。因此默认值测试通过并不能排除密集 IC 被截断。

另有测试仅设置 `component_id=None` 后断言 None，以及构造两个相同 Point 后检查距离为零，没有调用真实归属算法或图构建。这些是示例断言，不足以验收“拒绝错误 owner”和“无导线 pin 直接接触”。

建议：增加从真实配置加载到 decoder 的端到端配置测试；准备 16/32/64 引脚合成响应，检查实际解码与归属；统计真实图上 top-k 截断率。采用类别或可见边长驱动的预算，并保留全局上限，不能简单一律放大导致假阳性激增。

验收：调用真实 adapter/assignment/graph 路径；在密集 IC 上报告 cap 前后候选数、正确 pin 数、FP、编号 exact 和完整 PinF1，分别使用历史 4px 与指南 5px 口径。

### P1 虚拟补线记录在感知集成边界丢失

位置：[wire_vectorizer.py](E:/EDA挑战题目六/src/pcbparse/perception/wire_vectorizer.py:414)、[composite_provider.py](E:/EDA挑战题目六/src/pcbparse/perception/composite_provider.py:1511)。

vectorizer 已返回 virtual_repairs 和 break 信息，但 `_vectorize_masks` 只消费 polylines 与 junctions。闭运算修改了 mask，再从修改后的 mask 提取线段；新建 WireSegment 未继承这些虚拟补线标记。也就是说，底层报告“不是实线”的信息尚未到达实际 IR。

Graph 层新增的 gap repair evidence 是另一条路径，不能补回形态学闭运算时已合成且丢失来源的像素。当前因此不能宣称所有虚拟连接都已与可见线段完整分离。

建议：保存原 mask 与闭运算新增像素区域；将 repair 局部坐标恢复到原图，并关联受影响 polyline/segment。IR 区分可见几何和推测连接，Serializer 明确哪些几何可写入官方 edges。纯关系补线可影响候选连通，但不得自动伪装为图像实线。

验收：通过 CompositePerceptionProvider 的小 mask 夹具追踪到 IR 和最终 JSON，证明连接标记不丢失。另用邻近平行线、十字跨线和文字噪声图确认没有因 closing 改善断线而大量误并网。

### P1 器件库尚未参与实际解析

位置：[library_matcher.py](E:/EDA挑战题目六/src/pcbparse/knowledge/library_matcher.py:243)。

当前 retrieve_component 的调用仍局限于 knowledge 模块及测试/工具，没有在 perception、association 或 orchestrator 发现实际消费者。A07 自身也注明 wiring 留给 A06/A08。因此索引数量和 7 个夹具的召回率不能作为生产收益。

建议：在 OCR/Pin 候选形成后加一个默认关闭的候选补充阶段；仅写 evidence/candidates，先不直接覆盖字段。绑定 library hash，并把索引及相关配置带入 Docker。由统一关联器在视觉证据约束下选择或 UNKNOWN。

验收：开关对比必须能在 IR 中看到库候选来源；关闭时与基线一致；无型号、歧义型号和冲突 pin 时拒绝。除召回外，报告错误覆盖率和真实字段 exact。库的 unique pin number 数宜称为“库中观测编号数”，不要绝对等同某个封装的真实物理引脚数。

位置：[build_component_shadow_ab_a05.py](E:/EDA挑战题目六/scripts/build_component_shadow_ab_a05.py:88)、[component_shadow_ab.json](E:/EDA挑战题目六/artifacts/audits/component_shadow_ab.json)。

旧同数据 raw-v1 结果的检测 F1 增加约 0.079、Pin 检测 F1 增加约 0.111、pairwise Graph F1 增加约 0.090，但位号正确数 17/364 降至 10/364，value 8/272 降至 2/272。这说明不晋级有依据；也说明当前最大的可疑瓶颈是字段读取与绑定。以上不是这次代码改动后的测量，pairwise Graph F1 也不能替代严格标识下的官方 NetHypergraphF1。

### P2 OCR 原文保留与候选选择还需补一层

位置：[ocr_common.py](E:/EDA挑战题目六/src/pcbparse/association/ocr_common.py:133)、[ocr_multilevel.py](E:/EDA挑战题目六/src/pcbparse/perception/ocr_multilevel.py:349)。

原文不可变是正确的，但“原文保留”和“输出永远优先原始识别”不是同一件事。当前 preferred_text 优先 raw_text，需回归验证有明确证据的 resolved_text 修正是否还能生效。

同时，多视图去重仅在 match_key 不同时才把 suppressed raw_text 放入 candidates。`10k` 与 `10K` 的 match_key 相同，另一种大小写只留在 suppressed_duplicates 元数据，未必到达后续 exact 候选竞争。这使字段层新增的 exact 区分可能在上游已丢掉备选。

建议独立保存 raw_observation、candidate_values、selected_value 和 selection_evidence；所有不完全相同的原始读数都进入候选，空间重复去重不等于语义候选删除。增加“原始错误但证据确认的候选正确”和“大小写冲突必须拒绝或经证据选定”的跨模块测试。

## 4 下一轮实施顺序

### 第一阶段 补真实调用和测量

完成四项：修 A01 失败；把新 serializer/quality 接入 orchestrator 和 submission；A04 改为真实对象匹配而不是接收任意整数；生成当前集成快照。建议先做 5–10 张开发图的全链路冒烟，覆盖密集 IC、重复位号、跨线、飞线和空/坏输入。

退出标准：每张图都有可回放 IR、真实质量分类、非空指标和失败原因；不存在用 null/全零文件冒充已测结果；测试失败修复且相关集成测试通过。

### 第二阶段 解决密集引脚与补线证据

修复 cap 的配置测试和真实截断策略；把 vectorizer 证据传到 IR；补真实 provider 到 graph/serializer 的跨层测试。不要只增加独立 helper 测试。

退出标准：密集 pin 召回与 FP 均可解释；虚拟补线不会静默变成实线；图构建与 validator 在相同连接契约下工作。

### 第三阶段 OCR 与器件库联合消融

先按新错误漏斗判断 detector、recognizer 与 association 谁损失最大，再决定补读或训练。接入库候选开关；对大小写候选、resolved 值及重复位号做跨模块验证。对 YOLO 新框带来的 ROI、owner、文字邻接变化单独分析。

退出标准：位号、IC name、阻容 value、pin number/name 的 exact 与错误赋值率同时报告；不以非空率上升作为成功；检测提升不能掩盖 key 退化。

### 第四阶段 候选晋级与部署验证

固定 30 张开发 val，运行旧主锁与新候选的同版本 A/B，以及单因素/组合实验。独立工程族数据尚未补齐时，只报告开发回归。主锁仍保留，直到候选下游门禁通过。

Docker 冒烟、依赖检查、设备路径和超时控制可先在现有锁上做，不应全部等待独立 holdout；最终发布验收才要求绑定冻结后的候选。验证离线启动、坏图处理、连续批量、冷启动/P95、显存和三次确定性。GPU/平台依赖未在本次重测，不沿用旧结果冒充当前环境通过。

### 暂缓项目

暂缓大规模 QA 数据生成、全参数训练、多轮 RL 和复杂展示平台。A10 的最小错误复核功能可以随阶段三建设，用于保存当前真实失败案例；A11/A12 等到候选质量与收益可测后再做。
